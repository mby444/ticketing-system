# Repository guide

Single Next.js 16 (App Router) app — a support ticket system ("QuickTicket"). Not a monorepo. No test framework, no CI, no pre-commit hooks. `CLAUDE.md` is just `@AGENTS.md`; this file is canonical.

## Structure

- `app/` — routes: `/`, `/tickets`, `/tickets/[id]`, `/tickets/new`. Server components call server actions directly.
- `actions/ticket.actions.ts` — every server action (`"use server"`); mutations call `revalidatePath("/tickets")`.
- `lib/prisma.ts` — Prisma singleton; `lib/auth.ts` — jose JWT + `auth-token` cookie helpers; `utils/sentry.ts` — `logEvent()` wrapper used throughout instead of raw Sentry calls; `lib/cloudinary.ts` — server-only attachment helpers (validate/upload/destroy/thumbnail). **Never import it from a client component** — it pulls in the Cloudinary SDK; client forms duplicate the small size/MIME/count constants instead.
- `emails/` — React Email templates (`ticket-created.tsx`, `status-updated.tsx`, `new-comment.tsx`, shared `email-layout.tsx`); `lib/qstash.ts` — QStash producer helper (`EmailJob` type + best-effort `publishJob()`); `lib/email.ts` — worker-side dispatch (fresh DB read → template → Resend); `app/api/jobs/send-email/route.ts` — HMAC-signed worker endpoint.
- `lib/roles.ts` — `STAFF_ROLES`/`isStaff`, deliberately dependency-free (no `next/*` imports) so the QStash worker in `lib/email.ts` can check a role without dragging `next/headers` into the route bundle; `lib/authorization.ts` re-exports both, so existing imports are unaffected.
- Path alias `@/*` → repo root (see `tsconfig.json`).

## Commands

- On this machine PowerShell blocks `npm.ps1`/`npx.ps1` (execution policy) — use **`npm.cmd` / `npx.cmd`** or commands fail immediately.
- Dev: `npm.cmd run dev` · Lint: `npm.cmd run lint` (flat ESLint + `eslint-config-next`, lints the whole repo).
- Typecheck has no script: `npx.cmd tsc --noEmit`.
- There are no tests. Verification = lint → typecheck → `npm.cmd run build`.
- Reset + reseed DB: `db_fresh.bat` (= `prisma migrate reset && prisma db seed && prisma generate`). **Destructive**: the seed (`prisma/seed.ts`) deletes all users and tickets, and `migrate reset` re-runs the seed anyway. `*.bat` files are gitignored.
- Run a one-off script: `npx.cmd tsx <file>` — `tsx` is **not** installed locally; npx downloads it on first use (also required by the configured seed command, so seeding needs network).

## Prisma 7 (differs from Prisma ≤6 defaults)

- Config file is **`prisma7.config.ts`** (not `prisma.config.ts`) — holds the datasource URL and the seed command. Trust it over `PRISMA7_SETUP.md`, which is just a saved copy of the Prisma docs guide.
- Client is generated from `prisma/schema.prisma` into **`generated/prisma/`** — gitignored. Import it as `@/generated/prisma/client`. After a fresh clone or any schema change run `npx.cmd prisma generate` (also wired to `postinstall`); missing/stale generated files cause confusing TS errors.
- Postgres via driver adapter: `lib/prisma.ts` builds a `pg.Pool` from `DATABASE_URL` and passes `PrismaPg` to `PrismaClient`. The schema has no `url` — don't add one.
- Schema changes: `npx.cmd prisma migrate dev --name <name>` (migrations live in `prisma/migrations/`).
- Prisma reference skills are pinned by hash in `skills-lock.json` and mirrored into `.agents/skills/`, `.claude/skills/`, `.windsurf/skills/` (all tracked). Use them for Prisma questions; don't hand-edit the mirrors.

## Environment

`.env` is gitignored but present locally; required vars: `DATABASE_URL`, `AUTH_SECRET`, `SENTRY_AUTH_TOKEN`, plus `CLOUDINARY_CLOUD_NAME` / `CLOUDINARY_API_KEY` / `CLOUDINARY_API_SECRET` for ticket attachments (already populated locally; uploads fail fast with a clear error when missing), plus `QSTASH_URL` / `QSTASH_TOKEN` / `QSTASH_CURRENT_SIGNING_KEY` / `QSTASH_NEXT_SIGNING_KEY` (Upstash QStash — US region, see multi-region docs) and `RESEND_API_KEY` / `EMAIL_FROM` (`QuickTicket <onboarding@resend.dev>`) / `APP_URL` for the email pipeline (`APP_URL` must equal the ngrok tunnel URL while testing locally, because QStash publishes to `${APP_URL}/api/jobs/send-email`). Sentry DSN is hardcoded in `sentry.*.config.ts`; `next.config.ts` wraps the build with `withSentryConfig` (tunnel route `/monitoring`), so builds attempt source-map upload.

## Comment backlog — intentionally not implemented (recorded 2026-09-27)

Do not treat these as bugs; they were scoped out when the comment system shipped:

1. **Flat thread, no nested replies.** Despite the "two-way discussion" framing, there is no `parentId` self-relation — comments are a single chronological list per ticket. Nesting would need a nullable `parentId String?` on `TicketComment` plus a recursive component.
2. **No edit and no delete.** The only way a comment disappears is `onDelete: Cascade` when its ticket is deleted. `updatedAt` exists in the DB but nothing renders an "edited" marker.
3. **`getTicketById` swallows errors as 404 (known risk, accepted)**: its `catch` returns `null`, and `app/tickets/[id]/page.tsx` maps `null` → `notFound()`. Because `comments` is now part of that same `include`, a failing comment query makes the **entire ticket detail page 404** instead of surfacing an error. Deliberately left as-is (low likelihood, and the 404 hides internals); if it ever bites, the fix is to let `getTicketById` rethrow or to return a discriminated result rather than `null`.
4. No live updates — the thread re-renders on `revalidatePath` (i.e. after your own submit) but there is no polling/SWR, so another agent's reply only appears on manual refresh.
5. No comment counts on `/tickets` or `/dashboard` (same gap as attachment backlog #3), and no way to jump to a ticket's unread discussion.
6. No per-comment attachments — files are still ticket-level only.
7. No pagination and no rate limit on `addTicketComment`; a long thread renders every comment at once and a user can post as fast as the network allows. `MAX_COMMENT_LENGTH` (5000) is the only per-comment bound.
8. No audit trail for comments, and no moderation (no edit/delete for staff, no soft-delete).
9. The auto status bump only fires for `Open` → `In_Progress` on a staff reply. There are no other transition rules: a client can never move a ticket, staff can still set any status, and `Resolved`/`Closed` are not reopened by commenting (commenting on a `Closed` ticket is rejected outright).
